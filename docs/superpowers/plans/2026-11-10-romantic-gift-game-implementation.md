# «KitKat в чемодане» — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Создать иллюстрированную романтическую игру с четырьмя заданиями, локальным сохранением, письмом и тремя секретами в существующем React-проекте.

**Architecture:** React-компоненты сцен и заданий, один небольшой контекст прохождения и чистый reducer с типизированными событиями. Контент хранится отдельно от механик; прогресс версионируется и сохраняется в `localStorage`. Иллюстрации используются отдельными слоями, текст и управление остаются HTML; CSS-анимации и браузерное аудио позволяют обойтись без новых production dependencies.

**Tech Stack:** Существующие React 19, TypeScript, Vite 8, npm; CSS; Vitest + React Testing Library + jsdom для логики и компонентов; Playwright для Chromium/WebKit и production build.

**Spec:** [Концепция игры](../specs/2026-11-10-romantic-gift-game-design.md), [утверждённый макет](../../design/assets/main-scene-approved.png).

## Global Constraints

- Текущий репозиторий: React + TypeScript + Vite, GitHub Pages, `base: '/gift/'`.
- Приоритет: iPhone 17 Pro Max и мобильный Яндекс Браузер; портретный режим.
- Ровно четыре сумочки, четыре разных задания, свободный порядок, один ключ за каждое решение.
- Ровно три необязательных секрета; общее количество и счётчик впервые появляются в финале.
- Основное письмо и доступ к подарку не зависят от найденных секретов.
- Звук изначально выключен, фоновой музыки нет; голосовое запускается отдельным действием.
- Новые production dependencies требуют отдельного согласования согласно AGENTS.md.
- Не придумывать от имени пользователя реальные воспоминания, цитаты из песни, слова предложения или особенности близких и питомцев.
- 13 ноября владелец утвердил 12 пунктов: 10 платных подарков, недоступную машину за 1 000 001 и бесплатные ежедневные объятия/поцелуи. Награда — 1 000 000, покупки необратимы, описания скрыты до покупки. Список и цены определены в отдельной спецификации выше.

## Review Focus

1. **Обновление или закрытие страницы посреди действия:** сохраняется результат и устойчивое состояние задания, а не незаконченная анимация. Проверки: этапы 2 и 4.

## Как будем работать

Выбран **поэтапный вариант**: шесть частей основной игры и затем отдельный подарочный лист. Каждая часть заканчивается запускаемой версией, автопроверками и короткой инструкцией для владельца. Это позволяет проверить художественное направление и мобильное поведение до того, как на них будет построен весь сценарий.

Основную последовательность ведёт текущий исполнитель; независимые подготовку графики и проверку решений можно делегировать. Единую модель прогресса и её интеграцию выполнять последовательно, чтобы части не расходились в контрактах.

После выполнения части исполнитель сообщает, что доступно, что ещё впереди, результаты проверок и адрес запуска, затем останавливается для ручной проверки. По запросу владельца несколько частей можно выполнить подряд. Ошибки текущей части исправляются до перехода к следующей.

| Часть | Что можно проверить руками | Условие готовности |
| --- | --- | --- |
| 1. Живая главная сцена | Стол, четыре сумочки, крупный план, возврат, адаптация | Выглядит близко к макету и удобно нажимается на телефоне |
| 2. Первое задание и сохранение | Решить «Начало», получить ключ, закрыть и открыть страницу | Результат и частичный ответ восстанавливаются, повторного ключа нет |
| 3. Остальные задания | Пройти все четыре сумочки в любом порядке | Четыре разных механики дают ровно четыре ключа |
| 4. Сундук и письмо | Самостоятельно открыть сундук, прочитать письмо, послушать запись | Финал работает независимо от секретов, закрытие страницы не мешает продолжить |
| 5. Пасхалки и волшебство | Найти секреты, увидеть счётчик в конце, вернуться за пропущенным | Все три находки открывают бонус, основной подарок доступен при любом результате |
| 6. Личное наполнение и проверка | Пройти игру с настоящими текстами/фото/голосом на iPhone | Нет черновиков, сломанных медиа и блокирующих проблем основной игры |
| 7. Подарочный лист — отдельно | Выбор подарков по согласованным правилам | Определим после готовности основной игры |

Не публиковать промежуточные этапы автоматически. Для проверки на телефоне предложить локальный Vite по LAN (`npm run dev -- --host 0.0.0.0`) либо, по отдельному запросу владельца, GitHub Pages. Проверка по LAN подтверждает интерфейс и механику, но не перенос сохранений между LAN и Pages: это разные origin.

## Общие контракты

Зафиксировать имена в этапе 1–2; последующие части используют их, не создавая альтернативные модели прогресса.

```ts
type PouchId = 'beginning' | 'journey' | 'proposal' | 'family';
type SecretId = 'green-dress' | 'white-bueno' | 'black-g-class';
type Scene =
  | { kind: 'table' }
  | { kind: 'pouch'; pouchId: PouchId }
  | { kind: 'chest' | 'letter' | 'finale' };

type TaskDraft =
  | { kind: 'quiz'; questionId: string; selectedId: string | null; confirmed: boolean }
  | { kind: 'photo'; selectedId: string | null }
  | { kind: 'phrase'; selectedWordIds: string[] }
  | { kind: 'detail'; inspectedIds: string[] };

interface GameProgress {
  schemaVersion: 1;
  contentRevision: number;
  completedPouches: PouchId[];
  foundSecrets: SecretId[];
  drafts: Partial<Record<PouchId, TaskDraft>>;
  chestOpened: boolean;
  letterOpened: boolean;
  secondBottomOpened: boolean;
  scene: Scene;
}

type GameEvent =
  | { type: 'navigate'; scene: Scene }
  | { type: 'save-draft'; pouchId: PouchId; draft: TaskDraft }
  | { type: 'complete-pouch'; pouchId: PouchId }
  | { type: 'find-secret'; secretId: SecretId }
  | { type: 'open-chest' | 'open-letter' | 'open-second-bottom' }
  | { type: 'restart' };
```

- `TaskDefinition` — discriminated union с `kind: 'quiz' | 'photo' | 'phrase' | 'detail'`; у вариантов ответов/слов/деталей стабильные ID. Правильность определяется по ID, не по отображаемому тексту или координатам.
- `GameContent`: `revision: number`, `status: 'draft' | 'ready'`, `title`, `dedication`, `pouches: Record<PouchId, PouchContent>`, `letter: { paragraphs: string[]; voiceSrc?: string }`, `secrets: Record<SecretId, SecretContent>`, `bonusMessage: string`. `PouchContent` содержит заголовок, `task: TaskDefinition`, записку-награду; `SecretContent` — заголовок и текст. Все тексты — строки, без HTML из контента.
- `GameSession`: `{ progress: GameProgress; send: (event: GameEvent) => void; storageStatus: 'available' | 'unavailable' | 'recovered' }`, доступен через `useGame()`.
- `getKeyCount(progress): number` и `canOpenChest(progress): boolean` вычисляются из уникальных `completedPouches`; отдельного изменяемого счётчика ключей нет.
- Компоненты заданий получают `{ task, draft, onDraftChange, onSolved }` с типами соответствующего `kind`. При повторном осмотре завершённого задания показывается записка и результат, а не обязательное повторное решение.
- Анимации и текущая позиция голосовой записи не входят в сохранение. Успешное действие фиксируется **до** начала наградной анимации; её завершение не является условием выдачи ключа/открытия финала.

## Проверки и отчёт после каждой части

- Сначала тест на ожидаемое поведение, его осмысленное падение, затем реализация и зелёная проверка; не добавлять тесты, которые только повторяют внутреннее устройство компонентов.
- Прогонять весь быстрый unit/component набор и относящиеся к части E2E; полную браузерную матрицу — на финальной регрессии либо после изменения, которое затрагивает все маршруты.
- Проверки типов и production build входят в `npm run test:e2e`; тестовый результат не заменяет просмотр diff и визуальную проверку.
- В отчёте: доступный сценарий, точные результаты команд, ограничения этапа, локальный адрес и 3–5 действий для ручной проверки.
- Не фиксировать успех без фактического вывода команды. Если не установились браузеры/зависимости, назвать заблокированную проверку, продолжить доступные проверки и не выдавать её за выполненную.
- В конце предлагать Conventional Commit для текущей части, но не выполнять Git-операции без отдельного запроса.
